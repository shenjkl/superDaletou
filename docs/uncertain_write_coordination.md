## 旧自定义奖金来源声明增量

此写入是追加用户声明，正文包含评估标识、来源类别、可选历史期号、本人说明和确认项；IndexedDB 在调用服务前严格持久保存请求和 SHA-256 摘要。浏览器关闭后，页面可按原事件标识查询、继续同键请求、封止、对已封止声明关联同内容重试，或在明确终态后清理本机副本。说明正文会留存在本机浏览器 IndexedDB；不把会话令牌写入索引。

服务端在同一 SQLite `BEGIN IMMEDIATE` 事务内检查声明、封止及关联重试。`GET /api/custom-origin-declaration-writes` 查询原事件及摘要；`POST /api/custom-origin-declarations/fence` 与声明提交竞争，接受结果和封止结果只能有一个。数据库触发器拒绝已封止事件的迟到插入；同一封止最多有一个直接重试。完整性检查纳入封止表、重试表、摘要、唯一关系、外键和迟到写入触发器。其它来源资料上传、来源更正、开奖复核等写入口仍需逐项纳入 R52。

本轮只做源码静态审阅，未运行测试、启动服务或浏览器；浏览器真实 IndexedDB/Web Locks、HTTP 响应丢失、提交与封止并发、重启和数据库恢复连续性仍待验收。

## 目标与对象

不同浏览器、不同本机端口以及本机后台请求可能同时访问同一数据库。客户端生成的不同请求标识不能单独证明它们是不同业务操作：一个判断已经提交但响应丢失时，另一客户端仍可能再次保存。为此，在同一数据库内，以 `(operation, object_kind, object_key)` 作为协调对象，建立唯一的当前占用；个人判断的对象为其证据类型与标识，新假设草稿的对象为原判断标识。不同对象或不同操作类型不互相阻断。

占用不是时间租约：连接断开、浏览器关闭或服务重启后不能自动释放，否则迟到请求或尚未看到的已提交结果可能与新请求重叠。它只保护接入该协议的应用写入口；手动复制、回滚数据库或使用未经升级的外部程序不在同一事务域内。

## 当前实现与验证状态（2026-11-04）

- 服务端 `prepare_write` 在同一 SQLite 写事务中创建对象占用；其他浏览器使用新请求标识时收到 `object_occupied` 和当前请求摘要/状态。不同对象及判断、草稿两类操作彼此隔离。
- 提交和封止检查当前占用。封止与提交继续共用数据库写锁；关联重试以新请求标识把占用版本加一并转给新请求。

## Windows 登录启动写入增量（2026-11-03）

登录后启动开关现在复用更新写入日志。浏览器先持久保存请求，再提交；服务端持有 SQLite 写事务锁时读取或修改当前用户注册表，并读回目标状态后保存已接受结果。若进程在注册表修改后、SQLite 结果提交前中断，恢复时可按原键重试；用户选择封止时，服务端先检查注册表，已达到目标则记为已接受，否则封止并拒绝迟到的原请求。封止后可关联同一设置对象的新请求。读回状态不可用时维持未知，不把注册表错误描述为成功或确定失败。

## 事务与状态

所有占用检查、准备记录创建、业务提交、封止、处置和重试转移必须在同一 SQLite 数据库写事务中完成，并与已有 `BEGIN IMMEDIATE` 写入锁协调。以下顺序规定可观察结果，具体表名与接口字段由实现决定。

1. **准备：**客户端先持久化本机索引与恢复输入，再请求准备。服务端对输入规范化并计算摘要；若该对象无占用，则同一事务创建准备记录及占用。相同请求及摘要重复准备返回已有结果。不同请求发现占用时拒绝新建，并返回可供当前用户核对的原操作标识和状态；不得替换原占用。
2. **提交：**服务端在业务写事务中同时检查准备记录、输入摘要、对象和当前占用。提交成功与原业务记录一起生效；占用保持，直到结果由用户确认。原请求重发仍遵循同键同输入的幂等规则。
3. **结果不确定：**查询只报告 `unknown`、`committed`、`fenced`，未知时保留占用；查询不到的请求或缺失的准备记录不能作为释放依据。服务应支持已登录本机用户按对象发现当前占用，即使原浏览器的本机索引不可用，也能读取请求标识和摘要并核对、封止；发现接口不返回未提交的判断理由或假设正文。
4. **封止：**以原请求标识和摘要封止，封止与实际提交互斥；已提交则返回原结果，先封止则拒绝迟到提交。两种结果均保留占用，直到用户确认或发起关联重试。
5. **确认与释放：**用户查看已提交或已封止结果后显式确认。服务端重新核验该终态，并以当前请求标识及占用版本进行比较后，在同一事务追加处置记录并释放占用。重复确认返回相同处置结果；未知、引用不符或占用已指向后继请求时拒绝，不能释放后继占用。客户端只有在可核验确认结果后才删除本机副本；确认响应丢失时可按原标识幂等查询或重发确认。
6. **关联重试：**仅对已封止请求，在同一事务中验证当前占用、原对象、`retry_of` 和唯一直接重试约束，再创建新准备记录并将占用从原请求转移到新请求。迟到的旧确认不得清除新占用。重试使用新标识，并重新校验当前证据、业务状态和适用截止；旧封止和重试关系均保留。

为避免预备阶段“返回丢失、客户端又创建不同重试标识”，客户端应先以单个事务持久化新请求标识、原请求标识、目标对象和恢复输入，再调用准备。若准备响应丢失，可用**相同标识与相同输入**重试准备；未持久化“已发送”状态前不得发送业务提交。准备占用后用户放弃操作，需通过服务端封止和确认释放，不能直接删除本机索引。

## 升级与兼容

- 数据库迁移在启动时原子创建新结构和必要约束，不能重写既有判断、草稿、准备或封止记录。已存在的准备记录需逐条确定是否已有业务提交、封止或未知状态；如无法唯一、完整地恢复对象占用，记录为需人工处理并阻断受影响对象，不静默选一个。
- 面向用户的判断和草稿写入应统一走准备、占用和严格校验。旧页面或客户端若不支持协议，服务端返回明确的升级/重新加载提示；不能让旧接口绕过已有占用，也不能声称旧版尚未登记的在途写入获得了新协议的追踪保障。内部调用需逐一审计并按同一事务合同适配。
- 已有历史记录按原有审计方式可读，升级不追溯生成虚假的准备时间或处置记录。部署时需保证旧服务不再对同一数据库写入；如不能保证，不能启用该协调协议。
- 隔离恢复候选不运行占用、提交或确认。正式恢复和数据库连续性校验尚未实现；手动复制或回滚数据库可能让其与客户端记录不一致，不能由“未知”直接推断原数据库未提交。

## 必须验证的反例

| 场景 | 预期结果 |
|---|---|
| 两个浏览器对同一对象使用不同请求标识同时准备 | 最多一个获得占用，另一方可发现原标识并核对；不会各自提交。 |
| 同一对象第一次提交已成功但响应丢失，另一浏览器尝试新请求 | 原占用仍在，先返回原请求；只有确认或关联重试协议完成后才可继续。 |
| 准备或确认响应丢失，浏览器关闭后恢复 | 相同请求幂等恢复；未知不清除；确认后占用和审计一致。 |
| 封止、迟到提交、关联重试和旧确认并发 | 提交与封止只允许一种终态；原确认不能释放后继占用；重试最多一个直接后继。 |
| 不同对象或操作类型并发 | 允许各自进展，不因无关占用造成全局阻断。 |
| 旧客户端在新占用存在时直接提交 | 服务端拒绝，并提示升级；不能绕过占用。 |
| 存储失败、事务中断或进程崩溃 | 不出现无准备的业务提交、半个占用转移或虚假成功；恢复后按持久化记录核验。 |
| 准备记录、占用引用或处置链被破坏 | 完整性检查失败；业务操作不得据此放行或自动清理。 |
| 浏览器站点数据丢失 | 用户可通过服务发现占用并查验或封止；未提交的个人正文若未另存不能声称已恢复。 |

实现后除数据库与无套接字测试外，还需真实服务、浏览器重启、多标签页、多浏览器、失败注入和安全访问测试。本草案不提供这些测试结果。

## 固定排除范围预留增量（2026-11-03）

历史回测页在调用 `/api/holdout-reservations` 前，将快照、起止奖期、确认项、请求键和摘要写入严格持久 IndexedDB。刷新或连接状态不明后按原请求键和摘要查询；未知时可以继续相同请求或先封止。封止请求最多有一个直接关联重试，重试沿用相同快照和奖期范围。浏览器日志使用 Web Locks 协调同源标签页，终态核验后才能清理本机副本。

服务端增加 `GET /api/holdout-reservation-writes` 和 `POST /api/holdout-reservations/fence`。提交、封止、关联重试和预留结果在 SQLite `BEGIN IMMEDIATE` 写事务内处理；持有该写锁时另外执行只读范围审计，再提交结果，避免应用内相关写入在审计与固定之间插入。相同范围即使由不同请求键提交，也复用既有排除范围记录；相同请求键只能对应相同内容。不可变请求结果、封止、重试表及数据库触发器保护提交/封止互斥。完整性检查核对这些表的摘要、规范化输入、结果与排除范围关联、外键、唯一重试约束和触发器。

此范围仅覆盖排除范围固定入口；直接 Python 函数兼容旧的无请求键调用，浏览器 HTTP 写入口要求请求键。直接数据库写入、旧版外部客户端和数据库回滚不受此协议约束。此次只做源码静态审阅，未新增或运行测试，也未启动服务或浏览器。真实 IndexedDB/Web Locks、HTTP 响应丢失、封止并发、刷新及服务重启恢复仍待验收；因此不代表 AC76—AC79 或 R52 全部通过。
